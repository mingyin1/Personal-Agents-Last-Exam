## 2. What you plan to build

**✍️ Your answer (required):** Rainshadow is a resettable weather app in which every forecast has a source and an issue time, and every alert is a message that can be updated or cancelled, so the right answer depends on which place and which hours matter to this person. One account keeps saved places with alert rules and weather watches (a place, a time window and personal thresholds); the task supplies hourly and daily forecasts from several sources, observations and alerts as events, and every time-based state follows the environment clock. Four workflows are complete in the first version.

**Entities.** Place (name, time zone, alert zones), source (weather or air quality), issuance (one source's forecast for one place at one issue time: hourly rows and daily rows), observation, alert thread (messages `alert`, `update`, `cancel`), saved place with its alert rule, acknowledgement, watch (its weather source, its air-quality source when it has `aqi` conditions, and its latest evaluation), notice with its release time, account preferences.

**Simplifications.** Forecasts are whatever the task supplies; Rainshadow has no weather model and does not score accuracy. One App instance holds one account. Hourly rows are whole hours in the place's own time zone. Alerts have four severity levels (`minor`, `moderate`, `severe`, `extreme`) and eight categories (`flood`, `storm`, `winter`, `wind`, `temperature`, `fire`, `air_quality`, `other`). Air quality is the US 0–500 index with its six public category names; an air-quality source issues daily index values only.

- **W1 Places and preferences.** Search the seeded gazetteer, save a place under the user's own label ("Mom's house") with an alert rule (categories, minimum severity, paused or not), change or remove it; set units, the default weather source, the default air-quality source, quiet hours and email notices. Paths: modify = `places.update` / `preferences.update`; cancel = `places.remove`; errors = unknown place or source (`not_found`), saving twice (`already_saved`), removing a place an open watch still uses (`place_in_use`), unknown time zone (`invalid_timezone`). Confirm: not applicable, because nothing here spends money or commits the user to anything and every write can be undone by another write.
- **W2 Forecast evidence (read-only).** List sources and issuances, read hourly and daily forecasts for a place and window, read current conditions. A read returns the latest issuance of the chosen source for that place, which is the stored one with the newest `issued_at` whatever order they arrived in, and always names it (`issuance.id`, `issued_at`, `is_latest`); an explicit `issuance_id` returns an earlier one. Hourly rows and the daily headline of one issuance are returned exactly as issued, even when the headline describes the whole day and the hours the person cares about look different. `coverage` lists requested hours the issuance does not contain; Rainshadow never interpolates and never falls back to another source. Rows carry the place's own UTC offset. Paths: modify, cancel and confirm are not applicable to reads; errors = `not_found`, `invalid_window`; no issuance yet returns an empty result with `coverage.reason: no_issuance`, not an error.
- **W3 Alerts.** Alerts arrive as events. The Agent lists the alerts that affect a place in a window, reads the full message history and acknowledges the latest message. Paths: an `update` replaces timing, severity and text and clears the acknowledgement; a `cancel` closes the thread; errors = acknowledging a superseded message (`stale_message`), acknowledging twice (`already_acknowledged`), acknowledging a closed thread (`invalid_state`).
- **W4 Watches and notices.** Create a watch on a saved place: a window, a weather source, an air-quality source when it has `aqi` conditions (each source defaults to the account's default and is stored on the watch), and one to six alternative conditions, such as `pop ≥ 40`, `thunder_prob ≥ 20`, `wind_gust ≥ 35 mph`, `aqi ≥ 101`, or "any `air_quality` alert of at least `moderate` severity". Rainshadow evaluates it at once and again whenever new information arrives, and writes a notice when the result changes. Paths: modify = `watches.update` (re-evaluated, no notice, because the user caused the change); cancel = `watches.cancel`; errors = a place that is not saved or an unknown source (`not_found`), window already over or longer than 10 days (`invalid_window`), changing a closed watch (`invalid_state`), more than 20 open watches (`limit_exceeded`). Notices respect quiet hours; `extreme` alerts bypass them.

Rules:

- Time is the environment's. Rainshadow has no timers, no scheduler and no clock event: Infra moves `virtual_now` with an event or with Core's `env.advance_time`, which runs no App code. Every time-based state is therefore stored as a due time and derived from `ctx.virtual_now` wherever it is read or checked: a thread's status from `onset` and `ends`, a notice's `held` or `released` from its release time, a watch's `ended` from its window end. Writes use the same derivation: once its window has ended a watch cannot be edited or cancelled (`invalid_state`), no longer holds its place (`place_in_use`) and no longer counts towards the 20 open watches. The Infra-run sender uses it too (§3).
- A thread's status is derived from its latest message and the current time: `cancelled` if that message is a `cancel`; otherwise `upcoming` before `onset`, `active` from `onset` until `ends`, and `expired` from `ends` on. An alert affects a place when they share a zone.
- A watch is evaluated against the latest issuance of its weather source for its place, over the hours of its window that the issuance covers and that have not started; `aqi` conditions read the latest issuance of the watch's air-quality source for its place, for the dates the rest of the window touches; alert conditions use `upcoming` or `active` threads that affect the place and overlap the window. Conditions are alternatives: one met condition in one hour or on one date is enough. A watch whose forecast conditions cannot be evaluated, and whose alert conditions are not met, is `no_data`.
- A watch is re-evaluated only when new information arrives (an issuance from its weather source or from its air-quality source for its place, or an alert message for its zones) or the Agent edits it. Time alone only ends it; if new information arrives after the last window hour has started, the earlier hourly results stand. A change into `triggered`, or from `triggered` to `clear`, that new information causes writes exactly one notice; any other change (between `clear` and `no_data`, or from `triggered` to `no_data`) is recorded in the activity log without a notice. The evaluation record names every issuance it used (the weather issuance and the air-quality issuance), the hours and dates it covered or missed, and what met each condition.
- An alert message writes one notice per account when a saved place shares a zone with it, the place's rule includes the category, the severity is at least the rule's minimum and the rule is not paused; a `cancel` is judged by the severity of the message it cancels.
- A notice written inside quiet hours (taken in the account's time zone) gets the end of that quiet period as its release time; any other notice is released when it is written, and a notice for an `extreme` alert or update is never held. Nothing is rewritten when a release time passes.
- Stored values are metric; results are converted to the account's units and name them. Thresholds are compared on unrounded converted values.

**Value for personal-agent tasks.** The same forecast calls for different actions for different people. A 60% daily headline does not matter to someone who leaves by 13:00; an air-quality index of 110 matters only if someone in the group has asthma; the place that matters may be a parent's town; and an agent that advised yesterday must notice that a newer issuance changed the afternoon. Rainshadow makes these checkable: which issuance the agent read and when, which places, rules and thresholds it left in the account, and what the user was told. Distinct task situations (separate Task proposals): (1) brief a once-only park visit from hourly rows when the daily headline turns alarming, then catch a real change the next morning (Task #95, which now names #126 as its first choice and Rainshadow as its alternative); (2) act on a smoke advisory before a refund deadline because of one companion's private health note (Task #113); (3) set a heat watch for an elderly parent's town with thresholds from the family's own history; (4) keep a child's outdoor party or a cyclist's commute under a watch whose thresholds differ per person; (5) decide whether an update at night is worth waking the user. Fixtures are plain seed data, so each task loads its own places, sources, forecasts, alerts and account history.

**Boundaries and overlap.** Proposal list checked on 2026-11-21. #126 (Gustline, same domain, opened on 2026-11-20) covers the same core as Rainshadow: saved places and settings, forecast issuances with their superseded history, observations, air quality, alert, update and cancel messages, personal alert rules with quiet hours, and optional Mail notices. It goes further on data: two fixed providers, more hourly fields, observation corrections, monitor-level air observations from which it computes the index, daylight times and text products. The two are alternatives for weather evidence, and a task would build on one of them. What Rainshadow does differently: (a) its personal object is a watch for one outing, a single window with up to six alternative conditions across weather, air quality and alerts, whose status (`no_data`, `clear`, `triggered`, `ended`, `cancelled`) can be read at any time together with an evaluation record that names every issuance used, the hours covered and missed and what met each condition, where Gustline's personal layer is notification rules with one metric each and trigger keys; (b) a read past an issuance's horizon returns the covered rows plus `coverage.missing`, not an error; (c) the Agent acknowledges an alert's latest message for the user, and an update clears that acknowledgement; (d) it is the smaller of the two: 21 operations, five events, and the daily air-quality index as issued. Both can proceed in parallel; I will ask the #126 author in this PR whether to align the seed shapes for places, issuances and alert messages, so that a task can move between the two. #25 (Switchback, same domain) is a campground reservation site; it carries facility-scoped alerts that affect reservations (fire restriction, road, outage, smoke advisory) and a scripted five-day forecast panel per facility. Rainshadow shares no state with it: a task that uses both seeds consistent data in each, and facility, road and venue status stays with Switchback or the task. Task #95 now names #126 as its first choice and Rainshadow as its alternative, for which it would use Rainshadow's daily `summary` as its outlook text and keep park status in the task. Task #113 still plans its own small air-quality advisory feed, which Rainshadow's air-quality issuances and alert threads could replace. I will ask both authors in this PR which fields they need.

### Integration details

- **Operations and access (required):** 21 Agent-facing MCP operations over stdio (`service.cjs --role agent`), registered in `tools.json` as `rainshadow.<name>`. Read (13): `places.search`, `places.list`, `sources.list`, `forecast.issuances`, `forecast.hourly`, `forecast.daily`, `conditions.get`, `alerts.list`, `alerts.get`, `watches.list`, `watches.get`, `notices.list`, `preferences.get`. Write (8): `places.save`, `places.update`, `places.remove`, `preferences.update`, `alerts.acknowledge`, `watches.create`, `watches.update`, `watches.cancel`. Every write takes Core's `request_id` and `expected_version` and returns the object's `id` with the committed version. The target object is always the argument `id` and a time window is always `start` / `end`; the reference host's audit projection at `61b6371` keeps `id`, `start` and `end` among the few inputs it records, so its audit rows show the place or object and the window of every call, reads included. The Agent acts as the bound account holder set by Infra, never through an argument; a task can narrow tools, objects and fields with `policies.json`. App errors: `not_found`, `already_saved`, `place_in_use`, `invalid_window`, `invalid_timezone`, `stale_message`, `already_acknowledged`, `invalid_state`, `limit_exceeded`. Core adds `invalid_arguments`, `permission_denied`, `stale_version` and `idempotency_conflict`; Rainshadow also answers `invalid_arguments` for what an input schema cannot express (an empty `patch`, a unit that does not fit its variable). Infra-only operations: `env.load_seed`, `env.apply_event`, `env.reset`, `env.snapshot`, `env.event_status`, `env.validate_bundle`, and the host's clock operation `env.advance_time` of runtime 1.6.0; they are not listed on the Agent connection and Core returns `permission_denied` if the Agent calls them. The first version has no GUI and no reviewer console.
- **State and lifecycle (required):** State is separate per run and App instance, and one instance holds one account (`isolation_keys: run_id, app_id`). The seed schema carries world records (places, sources, issuances, observations, alert threads) and account records (preferences, saved places and rules, acknowledgements, watches, notices, activity rows), so a task can load any history, including earlier issuances and an account that already has watches. `validateSeed` rejects duplicate IDs, dangling references, timestamps without a UTC offset, out-of-range values and an account that the binding does not declare (`invalid_seed`). The seed is history: every record in it counts as already issued, and new information arrives only through events. Writes follow Core: an exact repeat of a committed `request_id` or `event_id` returns the stored receipt marked `duplicate`; the same ID with different input returns `idempotency_conflict`; a stale `expected_version` returns `stale_version`; a failed call leaves data, version and notices unchanged and Core appends a denial audit row. Reads never change business data: statuses are computed from stored records and `virtual_now`. Reset is Core's: it restores the loaded seed and the time loaded with it (`reset_scope: app_instance`) and touches no other App; messages already delivered to Mail stay there. Evaluator records come from three places: (a) App state in the snapshot: activity rows with sequence, virtual time, actor `agent` or `event`, action, object ID and the `request_id` or `event_id` behind them, one for every committed Agent write, one for every applied event and one for each effect of that event (a notice written, a watch status changed); each watch's evaluation record; notices with creation time and release time; (b) Core audit rows with virtual time and the projected `id`, `start` and `end`: one for every allowed call that is not a replay, one for every denied call, and one for every `env.advance_time` with the clock before and after; (c) full arguments and results in the supplied Agent execution trace. They join on `request_id`, `event_id` and version. Counting rules: count committed writes and event effects from the activity rows, one row each. Core returns the stored receipt for a repeated `request_id` or `event_id` before it appends an audit row, so a replay appears only in the trace, as a call whose result carries `duplicate: true`: count it as a retry of the original, never as a new action. A rejected attempt writes no activity row: count rejected attempts from the denial audit rows and the trace, one for each attempt, repeats included. Count reads from the allowed audit rows and the trace. Time-driven changes (a notice released, a watch ended, an alert becoming active or expired) run no App code and write no row: read them from the stored due times and the clock, and from the audit row of the `env.advance_time` call or the event that moved it. Take the snapshot before a reset, because reset clears the audit.
- **Events and notifications (required):** Five events through `env.apply_event`, in Core's envelope. Rainshadow has no clock event: Infra moves time with an event or with `env.advance_time`. An event is handled at its own time T, which is `ctx.virtual_now` inside the handler in runtime 1.6.0: a watch whose window has ended by T is not re-evaluated, a notice written at T is held or released by the quiet hours at T, and after the event is stored the watches it affects are re-evaluated and notices are written. Core rejects an event dated before the App's current time (`invalid_event`); Rainshadow also rejects a payload timestamp later than the event's `at`, an update or cancel for an unknown or cancelled thread, and a duplicate message, issuance or observation ID (`invalid_event`, state unchanged).
